## Anti-Patterns Verdict

**Does this look AI-generated? Mostly no — but with named, fixable tells.**

What rescues it from feeling like AI slop:

- The palette is disciplined (off-white stage, navy ink, single Signal Blue accent), not the SaaS purple-blue gradient cliché. No purple in the product.
- Typography is one family across all registers, with weight (300–900) and uppercase 10–11px / 0.08em-letterspaced labels doing the hierarchy work — exactly the Weight-Over-Family Rule, executed.
- CTAs are pill-shaped (`9999px`) consistently. Card corners are `12–18px`. The radii vocabulary is honored.
- The bottom-anchored learn-more sheet, the `shadow-sheet-up` upward cast, the `focus-halo` on the primary CTA, and the 30×30 Signal-Blue step badge all read as intentional design decisions — not stock components.
- No hero-metric template, no identical icon-card grid, no maple-leaves Canadiana, no Inter.

What still reads as a tell, with line numbers:

1. **`borderLeft: '3px solid ${BLUE}'` on the desktop pull-quote** — `LaunchpadApp.tsx:1080`. The Tinted-Border Rule and the Don't list both ban side-stripes >1px. This is the single most legible violation of the system's own rules.
2. **`filter: blur(18px)` on the desktop immersive backdrop** — `LaunchpadApp.tsx:1537`. DESIGN.md Don't: "Don't reach for glassmorphism outside the learn-more overlay." This is exactly the SaaS-cliché blurred-cover-photo treatment the document warns against.
3. **`backdropFilter: blur(...)` on FormatBadge, DesktopRailBtn, MobileRailBtn, SearchModal** — `LaunchpadApp.tsx:2163, 2290, 2331, 2532`. Five places where glass is used; only the learn-more overlay (globals.css:186) is sanctioned.
4. **`#fff` and `#000` literals everywhere** — 19 occurrences in `LaunchpadApp.tsx`, plus `'white'` at line 2671. The No-Pure-Neutrals Rule says "never `#000` and never `#fff` for text or large surfaces." The page.tsx body is explicit `'studio-off-white'` and the inverse should be `--white` only on elevated card surfaces.
5. **Em dash in user-facing copy** — `LaunchpadApp.tsx:2593` ("No matches yet — try…"). PRODUCT.md prohibits em dashes in copy. (Comments and section dividers in source code are fine; only this rendered string violates.)
6. **Hard-coded color constants at the top of `LaunchpadApp.tsx`** — `STAGE_BG = '#F6F6FF'`, `INK = '#22224C'`, `INK2 = '#485163'`, `BLUE = '#0092FF'`, `NAVY = '#22224C'`, `BORDER = '#E5E9F1'` (lines 58–64). The CSS variables `--off-white`, `--navy`, `--neutral-5`, `--blue`, `--neutral-2` already exist for these exact values. The component duplicates the token system instead of consuming it.

If a designer who hadn't read DESIGN.md saw the home feed first, the side-stripe and blurred backdrop would be the things that spark a "this looks like every Vercel template" reaction. Everything else is on-thesis.

## Detailed Findings by Severity

### P0 — Blocking

#### A11Y-1 · Most interactive elements have no visible focus indicator
- **Location:** `src/components/LaunchpadApp.tsx` — `CategoryChip` (~2222), `FormatChooser` button (2394), `FormatOption` (2459), `MobileRailBtn` (2312), `LearnMoreCta` button (126), `EmptyState` button (2718), `SearchModal` result button (2596), the desktop search trigger (904), the mobile header search button (1188).
- **Category:** Accessibility
- **Impact:** Keyboard users cannot tell where focus is on most of the home feed. The `.lp-overlay-rail-button` class at globals.css:120 only covers the desktop overlay rail; nothing else has a `:focus-visible` rule. Browsers may show a default outline for `<button>`, but it's stacked under custom borders/shadows and visually disappears on light pill backgrounds. This blocks AODA compliance, which PRODUCT.md commits to as a deployment requirement, not a stretch goal.
- **WCAG/Standard:** WCAG 2.1 AA — 2.4.7 Focus Visible (mandatory for AA); AODA IASR §14 references WCAG 2.0 AA but Ontario school deployments increasingly require 2.1 AA per AODA-aligned procurement.
- **Recommendation:** Add a `.lp-button` shared class (or a small set of variant classes) that always carries a `:focus-visible` rule producing a 3px Signal Blue halo on light surfaces and a 3px white halo on photographic/dark surfaces, mirroring the existing `.lp-overlay-rail-button` pattern. Apply the class to every inline-styled `<button>` in `LaunchpadApp.tsx`. Don't rely on the browser default — at this many surfaces, you need a token.
- **Suggested command:** `$impeccable harden`

#### A11Y-2 · Search input strips outline with no replacement
- **Location:** `src/components/LaunchpadApp.tsx:2569` — `SearchModal` `<input>` has `outline: 'none'` and no `:focus-visible` style. The wrapping container has its own border but it does not change on focus.
- **Category:** Accessibility
- **Impact:** A keyboard user who lands in the search field has no visual confirmation that they're typing into the right control. Compounds with A11Y-1 — once focus moves into the modal it's invisible. PRODUCT.md explicitly says "Visible focus state on every interactive element. Never `outline: none` without a replacement," and DESIGN.md repeats this for inputs in §5.
- **WCAG/Standard:** WCAG 2.1 AA — 2.4.7 Focus Visible.
- **Recommendation:** Replace with a wrapper that gains a 3px `var(--primary-blue)` halo on `:focus-within`, or apply `:focus-visible` directly to the input with a 2px Signal Blue ring. Either way: do not ship `outline: none` without the replacement.
- **Suggested command:** `$impeccable harden`

### P1 — Major

#### A11Y-3 · Touch targets below 44×44 across secondary controls
- **Location:** Learn-more sheet — `learn-more-action-button` is 34px tall and `learn-more-icon-button` is 34×34 (globals.css:271, 280); `MobileRailBtn` icon disc is 38×38 (`LaunchpadApp.tsx:2326`); `DesktopRailBtn` is 56×56 (passes); `CategoryChip` compact mode is roughly 32–34px tall (`LaunchpadApp.tsx:2230`); the desktop search trigger's `⌘K` chip is non-interactive but the search button itself is ~32px tall (`LaunchpadApp.tsx:904`).
- **Category:** Accessibility / Responsive
- **Impact:** Three of the four learn-more action controls (Related, Save, Share, Close) are 34px on mobile, where the sheet is the principal interaction surface. PRODUCT.md commits to AODA — Apple HIG and WCAG 2.5.5 AAA both prefer 44×44; WCAG 2.5.8 AA (2.2) requires at least 24×24 with adequate spacing. 34px passes the 24px minimum but fails the spirit of "every video play, filter, content card, and learn-more panel reachable and operable" on mobile, especially adjacent (8px gap) chips.
- **WCAG/Standard:** WCAG 2.5.8 (Target Size Minimum, AA, 2.2) — passes 24px floor; fails 2.5.5 (Target Size Enhanced, AAA, 44px).
- **Recommendation:** Bump the icon buttons to 40×40 minimum on mobile (`@media (max-width: 860px)`), keep 34px on desktop where pointer accuracy is higher. Increase `MobileRailBtn` icon disc from 38 to 44. Confirm 8px adjacency padding remains.
- **Suggested command:** `$impeccable adapt`

#### A11Y-4 · No `aria-labelledby` wiring on the learn-more dialog
- **Location:** `src/components/LearnMorePanel.tsx:104-108`. `Dialog.Content` does not pass `aria-labelledby` and `aria-describedby` is intentionally `undefined`.
- **Category:** Accessibility
- **Impact:** Radix Dialog auto-applies `role="dialog"` and `aria-modal="true"` and *does* auto-associate `Dialog.Title` via `aria-labelledby` when `Dialog.Title` is rendered — which it is at line 171. So this is partially handled. The remaining gap: the format/category chip metadata at the top of the sheet (lines 110–128) is the actual reading order students encounter first, and Radix labels the dialog by the `<h1>` title only. Screen readers will announce "Dialog · {item.title}" with no format/duration context until the user navigates further. PRODUCT.md asks for "meaningful headings" and the spec calls the chips "the signature typographic pattern of the system."
- **WCAG/Standard:** WCAG 2.1 AA — 4.1.2 Name, Role, Value (passes minimum); 1.3.1 Info and Relationships (the chip metadata is presented visually but has no programmatic association with the title).
- **Recommendation:** Either (a) wrap the format/category chips in a `<Dialog.Description>` element so Radix auto-wires `aria-describedby`, or (b) keep the manual `aria-describedby={undefined}` but add an `aria-label` on the `Dialog.Content` that combines `${item.format} · ${categoryLabel}` for screen reader users.
- **Suggested command:** `$impeccable harden`

#### A11Y-5 · YouTube iframe is `aria-hidden="true"` and has `pointer-events: none`
- **Location:** `src/components/LaunchpadApp.tsx:1748-1762` — the `YouTubePlayer` host div is `aria-hidden="true"` with `pointerEvents: 'none'`, and the iframe inside has `tabindex="-1"` (line 1703).
- **Category:** Accessibility
- **Impact:** Once a video is playing, screen-reader users have no way to access the YouTube player's own controls (captions toggle, scrubber, fullscreen). PRODUCT.md commits to "captions on all video" — captions are part of YouTube's UI, and this implementation hides that UI from assistive tech entirely. The keyboard scroll-overlay (`youtube-scroll-overlay` at 1872, 1986) intercepts the click area for "pause" but is also `aria-hidden`.
- **WCAG/Standard:** WCAG 2.1 AA — 1.2.2 Captions (Prerecorded), 1.2.5 Audio Description, 2.1.1 Keyboard.
- **Recommendation:** Drop `aria-hidden` and `tabindex="-1"` from the iframe once it's playing; let YouTube's controls be reachable. Add a separate, properly-labeled "Pause" `<button>` (visible or visually-hidden) for the scroll-overlay's pause behavior so screen readers can stop the video without reaching into the iframe.
- **Suggested command:** `$impeccable harden`

#### THEME-1 · Hard-coded color constants and inline hex literals bypass the token system
- **Location:** `src/components/LaunchpadApp.tsx:58-64` defines `NAVY`, `BLUE`, `STAGE_BG`, `SURFACE`, `INK`, `INK2`, `BORDER` as JS string constants. These then propagate through ~250+ inline-style usages. Plus 19 standalone `'#fff'` / `'#000'` literals (lines 1014, 1282, 1598, 1815, 1857, 1887, 1925, 1971, 2016, 2035, 2072, 2130, 2165, 2274, 2285, 2344, 2623, 2722, 2671/`'white'`) and one-off literals like `'#D9DFEA'` (2240) and `'#E6F4FF'` (2468).
- **Category:** Theming
- **Impact:** The `--navy`, `--blue`, `--off-white`, `--white`, `--neutral-2`, `--neutral-5`, `--secondary-blue-pale`, `--primary-blue` CSS variables already exist in `globals.css:9-49`. By duplicating their values as JS strings, the home feed cannot participate in any future theme switch (dark mode, high-contrast mode, or a co-branded variant), and any token edit requires hunting through `LaunchpadApp.tsx` instead of editing one CSS file. It also breaks the audit-trail value of having a token system.
- **WCAG/Standard:** Not directly a WCAG failure, but blocks AODA-aligned high-contrast-mode work.
- **Recommendation:** Move every color reference to `var(--token)`. Either (a) keep using inline styles but populate them from `var(--*)` strings, or (b) move to CSS classes / CSS Modules where the tokens compose naturally. The constants block at lines 58–64 should be deleted.
- **Suggested command:** `$impeccable distill`

#### THEME-2 · No dark-mode coverage anywhere in the system
- **Location:** `src/app/globals.css` defines a single `:root` token block with no `prefers-color-scheme` or `[data-theme="dark"]` variant.
- **Category:** Theming
- **Impact:** Students using device-level dark mode get a blast of off-white at 1am. PRODUCT.md doesn't explicitly require dark mode, but DESIGN.md's "tinted-neutral ramp" was clearly designed to support both light and dark surfaces, and AODA-aligned procurement increasingly asks for it. Today the page just doesn't respond to OS preference.
- **WCAG/Standard:** N/A — but related to WCAG 1.4.3 Contrast and 1.4.6 Contrast (Enhanced) when comparing dark-OS expectations.
- **Recommendation:** Defer if dark mode is not a P0 product commitment, but block this finding behind THEME-1 — until tokens are consumed instead of duplicated, dark mode is impossible to ship.
- **Suggested command:** `$impeccable colorize`

#### ANTI-1 · 3px Signal-Blue side-stripe on the desktop pull-quote
- **Location:** `src/components/LaunchpadApp.tsx:1078-1090` — `borderLeft: '3px solid ${BLUE}'`.
- **Category:** Anti-Pattern
- **Impact:** DESIGN.md §6 Don't: "Don't use `border-left` or `border-right` greater than 1px as a colored stripe accent. Side-stripes are an absolute ban — see the Tinted-Border Rule for the alternative." This is the single most legible self-violation of the system. It is also the LMS / Brightspace blockquote treatment the anti-references list calls out.
- **WCAG/Standard:** N/A.
- **Recommendation:** Replace with the system's intended pattern: an UPPERCASE 11px / 800 / 0.1em Signal-Blue eyebrow ("Pull quote" or no eyebrow), the quote in 17px / 500 italic Anchor Navy, and either no border or a 1px Slate Frame Light top rule above the eyebrow.
- **Suggested command:** `$impeccable distill`

#### ANTI-2 · Glassmorphism applied to five surfaces beyond the sanctioned overlay
- **Location:**
  - `LaunchpadApp.tsx:1522-1554` — `ImmersiveBackdrop`: full-bleed cover image with `filter: blur(18px)`, scale 1.08, opacity 0.82, plus a navy gradient on top.
  - `LaunchpadApp.tsx:2163` — `FormatBadge`: `rgba(255,255,255,0.14)` + `backdropFilter: blur(10px)`.
  - `LaunchpadApp.tsx:2290` — `DesktopRailBtn`: `rgba(8,8,26,0.62)` + `backdropFilter: blur(10px)`.
  - `LaunchpadApp.tsx:2331` — `MobileRailBtn`: `rgba(255,255,255,0.85)` + `backdropFilter: blur(8px)`.
  - `LaunchpadApp.tsx:2532` — `SearchModal` overlay: `rgba(8,8,26,0.6)` + `backdropFilter: blur(8px)`.
- **Category:** Anti-Pattern / Performance
- **Impact:** DESIGN.md §6 Don't: "Don't reach for glassmorphism outside the learn-more overlay. The 8px backdrop-blur on the sheet wash is the only blurred surface in the system." This rule is broken on the most visually prominent surface of all (the desktop home feed's whole backdrop), plus the rails and the search modal. `backdrop-filter` is also one of the heaviest paint ops in the browser; on a page that's already running a YouTube iframe and a transition deck, this is a real perf cost on mobile.
- **WCAG/Standard:** N/A directly. Indirectly impacts 1.4.11 (Non-text Contrast) — semi-transparent rail buttons over photo backgrounds rarely hit 3:1.
- **Recommendation:** `ImmersiveBackdrop`: replace with a flat Studio Off-White stage and let the 9:16 media tile carry the imagery (this matches what DESIGN.md §1 actually describes — "the stage is Studio Off-White … bright, calm, low-commitment"). The rails and `FormatBadge` should adopt the established navy-tinted ramp (Anchor Navy at 80% opacity, 1px Slate Frame Mid border, no blur). The `SearchModal` overlay can keep the dim but should drop the blur — or accept that this is a second sanctioned glass surface and update DESIGN.md to say so.
- **Suggested command:** `$impeccable distill`

#### ANTI-3 · Pure `#fff` and `#000` literals violate the No-Pure-Neutrals Rule
- **Location:** 19 `'#fff'` / `'white'` and 4 `'#000'` literals in `LaunchpadApp.tsx` (full list above in THEME-1).
- **Category:** Anti-Pattern / Theming
- **Impact:** The No-Pure-Neutrals Rule is the second-named rule in DESIGN.md §2: "Never `#000` and never `#fff` for text or large surfaces. Studio Off-White carries page background; Pure White is reserved for elevated card surfaces." Most uses are on text sitting over photographic media (where `#fff` is debatable but DESIGN.md still wants `var(--white)`), and several `'#000'` uses are large surfaces (`background: '#000'` at 1815, 1925, 2072, 2623) that should be Anchor Navy or Slate Deep per the ramp.
- **WCAG/Standard:** Indirect — DESIGN.md rule, not WCAG.
- **Recommendation:** Replace `'#fff'` with `var(--white)` and `'#000'` (large surfaces) with `var(--navy)` or a new `--media-letterbox` token. Pure white on photo overlays is contextually defensible, but it should still come from a token so future theme work can override it.
- **Suggested command:** `$impeccable distill`

#### ANTI-4 · Em dash in user-facing copy
- **Location:** `src/components/LaunchpadApp.tsx:2593` — "No matches yet — try "internship" or "feedback""
- **Category:** Anti-Pattern (brand voice)
- **Impact:** PRODUCT.md voice rules ban em dashes in copy. One sentence, one fix; the source-code comments and section dividers in this file are fine because they aren't rendered.
- **WCAG/Standard:** N/A.
- **Recommendation:** Rewrite as "No matches yet. Try 'internship' or 'feedback'." or "No matches yet · try 'internship' or 'feedback'."
- **Suggested command:** `$impeccable clarify`

### P2 — Minor

#### PERF-1 · `LaunchpadApp.tsx` is a single 2,746-line client component
- **Location:** `src/components/LaunchpadApp.tsx` (whole file). One existing dynamic import for `LearnMorePanel` (line 52) — good — but everything else (DesktopStage, MobileStage, FeedMediaDeck, YouTubePlayer, SearchModal, FormatChooser) ships in the same client bundle.
- **Category:** Performance
- **Impact:** First-paint TTI on slow connections is dominated by this bundle. The mobile-only `MobileStage` and the desktop-only `DesktopStage` render conditionally on `useIsMobile()`, but both ship to every device. The `SearchModal` only renders when ⌘K is pressed but is in the initial bundle. The `YouTubePlayer` only matters once a play button is clicked but loads YouTube's iframe API regardless.
- **Recommendation:** Split `SearchModal`, `YouTubePlayer`, and the inactive `MobileStage`/`DesktopStage` behind `next/dynamic` with `ssr: false`. The biggest win is `YouTubePlayer` — defer it until the first `playItem` call.
- **Suggested command:** `$impeccable optimize`

#### PERF-2 · Raw `<img>` tags for all media (no `next/image`)
- **Location:** `LaunchpadApp.tsx:1526, 1817, 1932, 2080, 2628`; `LearnMorePanel.tsx:163`. Every image carries an `eslint-disable-next-line @next/next/no-img-element` comment, indicating the warning was intentionally suppressed.
- **Category:** Performance
- **Impact:** No automatic responsive `srcset`, no AVIF/WebP, no lazy loading by default, no priority hints. The full-bleed immersive backdrop and the 9:16 media tile both load the same source URL at full resolution. On mobile the `ImmersiveBackdrop` isn't rendered (mobile uses `MobileStage` which has its own `<img>`), so this is wasted bytes mainly on desktop, but the next-card-peek thumbnail (line 2080) and search-result thumbnails (2628) compound it.
- **Recommendation:** Migrate to `next/image` with `sizes` props matched to the surfaces. Set `priority` on the visible `MediaStage` image; lazy-load the next-card peek and search-result thumbnails. This also unlocks the `placeholder="blur"` treatment which would cleanly replace the 18px `filter: blur` hack in `ImmersiveBackdrop`.
- **Suggested command:** `$impeccable optimize`

#### PERF-3 · 18px backdrop blur on a scaled cover image is a hot paint
- **Location:** `LaunchpadApp.tsx:1530-1541` — `ImmersiveBackdrop` has `transform: scale(1.08)`, `filter: blur(18px)`, `opacity: 0.82`, plus a sibling 100%-coverage gradient.
- **Category:** Performance
- **Impact:** `filter: blur()` at 18px on a `100vw × 100vh` image forces a full repaint each frame the underlying image changes (which it does on every feed transition). On Apple Silicon this is fine; on a Chromebook running a Brightspace tab next to it, this is the kind of effect that drops the feed transition below 60fps. Also: this isn't visible-by-design — DESIGN.md doesn't ask for it.
- **Recommendation:** Drop the backdrop entirely (preferred — see ANTI-2) or pre-render a static blurred poster server-side via Next.js' image-optimization pipeline.
- **Suggested command:** `$impeccable optimize`

#### PERF-4 · Body scroll lock on the learn-more sheet uses `position: fixed; top: -y`
- **Location:** `src/components/LearnMorePanel.tsx:61-81`.
- **Category:** Performance / Reliability
- **Impact:** The standard pattern for body scroll lock on iOS, but it shifts layout (causes a single forced reflow on open and close) and it interacts poorly with anchor-link restoration. Not broken — works as intended — but `overflow: hidden` on `<html>` plus `scroll-padding-top` is now better-supported and avoids the forced reflow.
- **Recommendation:** Consider migrating to `overflow: hidden` on `documentElement` or use Radix's `Dialog.Root`'s built-in scroll-lock (which it does by default — this manual implementation may be double-locking).
- **Suggested command:** `$impeccable optimize`

#### RESP-1 · Filter rail forces horizontal scroll on mid-range desktops
- **Location:** `LaunchpadApp.tsx:937-974`. Outer wrapper has `overflowX: 'auto'`, inner row has `width: 'max-content'` and `margin: '0 auto'`. With 8 categories at ~150–180px each, the row needs ~1300px before "For you" is included.
- **Category:** Responsive
- **Impact:** On a 1280px desktop, the chips are scrollable instead of fitting — students don't realize there's a chip behind the right edge. Auto-scroll behavior on Chromebook trackpads is also inconsistent.
- **Recommendation:** Either (a) drop to abbreviated labels at this width (the `categoryShortLabel` helper already exists for mobile and could be applied at < 1380px), or (b) wrap to a second line. The existing `width: max-content` + `margin: auto` pattern is fine on 1440+ but should fall back gracefully.
- **Suggested command:** `$impeccable adapt`

#### RESP-2 · `height: '100vh'` on the navigation surface
- **Location:** `LaunchpadApp.tsx:864, 1163` — both `DesktopStage` and `MobileStage` use `height: '100vh'`.
- **Category:** Responsive
- **Impact:** On iOS mobile Safari, `100vh` includes the URL bar, so the bottom of the feed gets pushed off-screen until the user scrolls (which is disabled here because of `overflow: hidden`). The CSS `100dvh` (dynamic viewport height) is already used in `globals.css:196` for the learn-more sheet — the page shell should match.
- **Recommendation:** Replace `100vh` with `100dvh` (with a `100vh` fallback for older browsers). Same fix anywhere else `100vh` appears as a primary dimension.
- **Suggested command:** `$impeccable adapt`

#### A11Y-6 · Animations in `LaunchpadApp.tsx` are not gated by `prefers-reduced-motion` at the CSS level
- **Location:** `LaunchpadApp.tsx:1442-1467` (FeedMediaDeck transitions), `1419-1440` (nudging transform), `2236, 2288` (CategoryChip / DesktopRailBtn transitions), `2678` (Toast transition).
- **Category:** Accessibility
- **Impact:** The component does branch on `reducedMotion` for the feed-deck transitions (lines 1370–1383, 1447–1448) and the nudge effect (1401), so functionally it's mostly handled. But the smaller transitions (`transition: 'all 160ms var(--ease-standard)'` on chips, the toast `translateY` animation, the search modal entrance) don't honor `prefers-reduced-motion`. PRODUCT.md commits to honoring it "for every animation" — every is the operative word.
- **WCAG/Standard:** WCAG 2.1 AA — 2.3.3 Animation from Interactions (AAA, but a stated commitment).
- **Recommendation:** Add a global CSS rule: `@media (prefers-reduced-motion: reduce) { *, *::before, *::after { animation-duration: 0.01ms !important; transition-duration: 0.01ms !important; } }` in `globals.css`, then keep the JS-level `reducedMotion` branch only where logic differs (e.g., the feed transition needs to swap to an instant set rather than animate to `translateY(0)`).
- **Suggested command:** `$impeccable harden`

#### A11Y-7 · Toast is positioned but not announced to screen readers
- **Location:** `LaunchpadApp.tsx:2661-2686`. The `Toast` component renders a `<div>` with no `role="status"` or `aria-live="polite"`.
- **Category:** Accessibility
- **Impact:** "Saved · check back anytime" and "Link copied" are state-change feedback the user just triggered. Without a live region, screen-reader users hear nothing.
- **WCAG/Standard:** WCAG 2.1 AA — 4.1.3 Status Messages.
- **Recommendation:** Add `role="status"` and `aria-live="polite"` to the toast wrapper. Confirm the `pointerEvents: 'none'` doesn't suppress announcement (it shouldn't).
- **Suggested command:** `$impeccable harden`

#### A11Y-8 · `<h1>` reused per content item without a single page-level `<h1>`
- **Location:** `LaunchpadApp.tsx:1029` (DesktopStage), `LearnMorePanel.tsx:172` (sheet title). The brand wordmark "Career LaunchPAD" at line 890 is a styled `<div>`, not an `<h1>`.
- **Category:** Accessibility / Semantic HTML
- **Impact:** The page has multiple `<h1>` elements depending on which content card is active, and the sheet adds another `<h1>`. While modern accessibility guidance allows multiple `<h1>` in semantically-sectioned documents, the brand title (which is the actual page-level header) isn't a heading at all. Screen-reader heading navigation will jump straight to the content title with no page-level anchor.
- **WCAG/Standard:** WCAG 2.1 AA — 1.3.1 Info and Relationships.
- **Recommendation:** Wrap the brand wordmark in `<h1>Career LaunchPAD</h1>` (visually styled, semantically the page title), demote the per-item content title to `<h2>`, and demote the sheet title to `<h2>` as well (the sheet is a sub-document). Or keep the per-item title at `<h1>` but add a visually-hidden page `<h1>` at the top.
- **Suggested command:** `$impeccable harden`

#### ANTI-5 · `Highlighted Title` accent block uses pure `#fff` text inside the Signal-Blue chip
- **Location:** `LaunchpadApp.tsx:2127-2136`.
- **Category:** Anti-Pattern (No-Pure-Neutrals Rule)
- **Impact:** Same rule as ANTI-3 but worth flagging separately because it's the brand-defining typographic moment of the home feed. Pure white text on `#0092ff` actually has fine contrast (4.55:1, just over AA), so this is borderline by accident, not by design — Pure White from the token set would render identically and be on-thesis.
- **Recommendation:** Replace `'#fff'` with `var(--white)`.
- **Suggested command:** `$impeccable polish`

### P3 — Polish

#### TYPE-1 · Open Sans loaded via `@import url(...)` rather than `next/font`
- **Location:** `src/app/globals.css:6` — `@import url('https://fonts.googleapis.com/css2?family=Open+Sans:wght@300;400;500;600;700;800&display=swap');`
- **Category:** Performance / Theming
- **Impact:** Next.js' `next/font/google` integration self-hosts Google Fonts at build time (no runtime fetch from googleapis.com), avoids the FOUT/FOIT race, and supports `font-display: optional`. The current `@import` adds a render-blocking request to a third-party origin, which on a slow Canadian school network is noticeable. Also: the `@import` doesn't request weight 800 — wait, it does request 800. But it doesn't request 900, and `LaunchpadApp.tsx` uses `fontWeight: 900` in 11 places (titles, step badges, brand mark, article copy). Those will be synthesized by the browser, which typically renders as fake-bold and breaks the typographic crispness DESIGN.md is built around.
- **Recommendation:** Migrate to `next/font/google` with `weight: ['300', '400', '500', '600', '700', '800', '900']` (DESIGN.md §3 explicitly lists 300–900). Remove the `@import` rule. This also fixes: the missing 900 weight, the third-party request, and the ability to set `font-display: optional` for AODA-favorable performance.
- **Suggested command:** `$impeccable typeset`

#### POL-1 · Decorative `transform: rotate(-2deg)` on the desktop category pill
- **Location:** `LaunchpadApp.tsx:1009`. The category pill is rotated `-2deg` and "Item N / M" reads as positional decoration.
- **Category:** Anti-Pattern (subjective)
- **Impact:** A small intentional touch that humanizes the layout — fine on its own. But combined with the `HighlightedTitle` accent block and the side-stripe pull-quote, the "left column" of the desktop stage is doing three different "this is editorially designed" gestures. DESIGN.md prefers restraint. This is a subjective polish call, not a violation.
- **Recommendation:** Pick two of the three (rotated chip + highlighted title is already enough). Drop or normalize the rotation if/when ANTI-1's side-stripe is removed and replaced with an eyebrow.
- **Suggested command:** `$impeccable distill`

#### POL-2 · `void Clipboard;` to suppress unused import
- **Location:** `LaunchpadApp.tsx:2745-2746`.
- **Category:** Code health
- **Impact:** Dead-import marker. Not visible to users. Either use it or remove it.
- **Recommendation:** Remove `Clipboard` from the import list and delete the `void` line.
- **Suggested command:** `$impeccable polish`

## Patterns & Systemic Issues

1. **Token system exists but is bypassed in the home feed.** `globals.css` has a complete brand-token block (lines 1–91), and the learn-more sheet's CSS *uses* it (`var(--navy)`, `var(--off-white)`, `var(--primary-blue)`, etc.). `LaunchpadApp.tsx` was apparently written before or independently of that work, and re-implements the same colors as JS string constants. Every theming finding above is a symptom of this single gap.

2. **Inline styles are doing too much.** A 2,746-line component with hundreds of inline `style={{}}` blocks is doing both layout and tokenization in the worst place to do them — the runtime, per render. Even setting aside the theming consequences, the maintenance pain shows up as: focus rings can't be applied via CSS, hover states are absent (inline styles can't express `:hover`), reduced-motion gating has to be duplicated in JS.

3. **A11y is mostly thoughtful, with predictable gaps where styling is inline.** The CSS-defined surfaces (`.lp-overlay-rail-button`, `.learn-more-cta__button`, `.learn-more-card`) all carry `:focus-visible` and `prefers-reduced-motion` rules. The inline-styled surfaces don't. The shape of the gap maps exactly to "did this component get a class name."

4. **Glassmorphism creep.** DESIGN.md sanctions blur on exactly one surface (the learn-more overlay). The implementation has it on five. This is the most common path from "intentional design system" to "AI slop" and it should be a hard stop in code review.

5. **Performance is not a current concern but the seeds are visible.** No `next/image`, no further code-splitting, multiple expensive paint ops (`filter: blur(18px)`, `backdropFilter: blur(10px)` × 5). Today the dataset is small and the YouTube iframe dominates the perf budget anyway. If the content set scales, these become real numbers.

## Positive Findings

- **Brand voice executed.** PRODUCT.md asks for "curious, confident, current," and the implementation delivers: pull quotes, format chips, the 9:16 immersive media tile, the "Scroll for more" affordance with chevron, the rotated category pill. None of this reads as Brightspace.
- **DESIGN.md is unusually clear.** Naming the rules ("One Spark," "Up-Cast Exception") makes audit findings easy to write — this is excellent design-system hygiene.
- **Learn-more sheet is close to spec.** `LearnMorePanel.tsx` + the `.learn-more-*` CSS section is almost entirely on-brand: pill icon buttons, uppercase 10px label chips, the `shadow-sheet-up`, the navy-tinted overlay, the 8px blur as the *one* glass surface, `prefers-reduced-motion` honored at the keyframe level (globals.css:539-555), and Dialog.Root + Dialog.Title wiring focus-trap and labelling for free.
- **Radix Dialog is doing the heavy a11y lifting.** Modal trap, focus restore, ESC handling, `aria-modal` are all handled by `@radix-ui/react-dialog` — this is the right primitive to reach for and the app uses it correctly.
- **`prefers-reduced-motion` is wired into the JS state machine.** The `usePrefersReducedMotion` hook plus the `reducedMotion` branch in `FeedMediaDeck` (lines 1370–1383, 1447–1448) shows a deliberate effort to respect the preference at the logic level, not just the CSS level. Most teams forget this entirely.
- **The keyboard story is mostly thought-through.** ⌘K opens search, J/K and ArrowUp/ArrowDown step the feed, Space toggles play, ESC closes the search modal, `isInteractiveShortcutTarget` correctly guards against typing into form fields. The remaining gap is visibility of focus, not the shortcut grammar.
- **Type system is honest.** `src/types.ts`, `applyContentFilters`, `orderContentForFeed`, `getYouTubeId`, `formatDuration` — content shape is well-typed, helpers are centralized in `src/lib/content.ts`. This makes the home feed easy to refactor without breaking logic.
- **No autoplay-with-sound by default.** The autoplay state machine at `LaunchpadApp.tsx:1689-1701` correctly probes `getAutoplayPolicy('mediaelement')` and falls back to muted — this is exactly what PRODUCT.md asks for.
- **Pill-shaped CTAs and uppercase labels are everywhere they should be.** The signature typographic pattern (10–11px / 800 / 0.08–0.12em uppercase) is consistently applied. DESIGN.md's Uppercase-Label Rule is honored.
